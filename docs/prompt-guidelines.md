# 프롬프트 지침

Claude Code에게 작업을 지시할 때 적용되는 규칙과, 지금까지 내려진 지시의 기록이다.
새로운 지시나 규칙이 생기면 이 문서에 누적한다. 아키텍처·빌드 명령 등 코드 구조에 대한 설명은 `CLAUDE.md`를 따르고, 여기서는 **작업 방식과 결정 사항**을 다룬다.

> 마지막 업데이트: 2026-10-19

---

## 1. 상시 적용 규칙

### 커뮤니케이션
- 답변(설명, 계획, 보고)은 **한국어**로 작성한다. 코드·식별자는 원문 그대로 둔다.
- 지시의 의도가 불분명하거나 정보가 누락된 경우, 임의로 구현하지 말고 질문한다.

### 작업 흐름
- 계획을 요청받으면 코드를 바로 작성하지 않고 `plan` 스킬로 `.claude/plans/`에 계획서를 먼저 만든다.
- PR 생성은 `create-pr` 스킬을 사용한다. PR 본문은 Issue / Work Description / Screenshot / To Reviewers 템플릿을 따른다.
- 브랜치는 `feat/<이슈번호>`, `fix/<이슈번호>` 형식을 사용한다.
- 커밋 메시지는 `<type>: <한국어 요약>` 형식이다. (`feat`, `fix`, `chore`, `docs` 등)
- 코드 변경 후 빌드(`./gradlew assembleDebug`)에 성공하면 **별도 요청 없이 커밋**한다. 빌드가 실패하면 커밋하지 않고 원인을 보고한다.
  - 커밋 시점에 `main`에 있으면 작업 브랜치(`feat/<이슈번호>` 등)를 새로 만든 뒤 커밋한다. 이슈 번호가 없으면 작업 내용으로 브랜치명을 짓는다.
- 하나의 구현을 커밋 하나로 몰지 않고, **리뷰하기 좋은 적당한 단위로 커밋을 나눈다**.
- **이슈 단위 작업**: 이슈 수정을 지시받으면 `main`에서 `feat/<이슈번호>` 브랜치를 알아서 만들고, 구현이 끝나면 push 후 PR까지 올린다.
  - PR base는 `main`이다. (`create-pr` 스킬은 `develop`을 가정하지만 저장소에 `develop` 브랜치가 없다)
  - 저장소에 `feature` 라벨이 없으므로 기능 작업은 `enhancement`, 버그는 `bug`, 문서는 `documentation` 라벨을 쓴다.
  - 리뷰어: 현재 저장소 협업자가 `HamBP`(본인)뿐이라 리뷰어 지정이 되지 않는다. 협업자가 추가되면 지정한다.
- 이슈가 아닌 작업은 push·PR을 자동으로 하지 않는다.

### 문서 유지
- 프롬프트를 받으면 작업 전에 `docs/` 문서를 먼저 참조한다. (`CLAUDE.md`에 명시되어 매 세션 자동으로 적용됨)
- 프롬프트마다 docs 수정이 필요한지 판단하고, 필요하면 바로 수정한다.
- `docs/` 아래 문서는 별도 요청이 없어도 개발이 진행될 때마다 함께 갱신한다.
  - `docs/prompt-guidelines.md` (이 문서): 새 지시·규칙·결정 사항을 추가
  - `docs/features.md`: 기능이 추가·변경·제거되면 반영
- 문서 갱신은 해당 기능 작업과 같은 브랜치/PR에 포함한다.

### 다국어
- 사용자에게 보이는 문자열은 하드코딩하지 않고 문자열 리소스로 관리한다.
- base 로케일은 한국어(`values/strings.xml`)이며 `values-ko/`는 만들지 않는다.
- 새 문자열은 `values`, `values-en`, `values-ja`, `values-es` **4곳**에 추가한다. (중국어는 제거됨 — 아래 기록 참고)
- 플레이스홀더(`%1$d` 등)는 모든 로케일에서 일치시킨다.

### UI / 디자인
- 디자인은 Figma 시안을 기준으로 한다(색상 팔레트, 아이콘 순서 등).
- 폰트 크기는 **12sp 이상**으로 한다.
- 효율 계산에 포함되지 않는 로그 타입(`includeEfficiency = false`)은 고유 색상 대신 **중립색**으로 표시한다.
- 다크 테마를 기본으로 하며, 포인트 컬러는 그린(`WorkGreen`)이다.

### 데이터
- 시간은 epoch **초** 단위로 저장한다. SQL 날짜 연산이 이를 전제로 한다.
- 현재 DB는 `fallbackToDestructiveMigration()`을 사용한다. 기획이 안정화되면 실제 마이그레이션으로 교체해야 한다(TODO).
